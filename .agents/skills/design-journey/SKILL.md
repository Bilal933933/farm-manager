# رحلة تحسين التصميم (Design Journey)

خط أنابيب كامل لسطح واحد متماسك في كل دورة: اختيار ← تدقيق ← نتائج ← خطط ← تنفيذ ← تقرير. يعمل **بأمر إطلاق واحد صريح** (اسم السطح أو "ابدأ") ثم يسير بلا توقف حتى نهاية السطح.

## 1. نموذج الاستقلالية (Autonomy)

- أمر واحد صريح بالنطاق يكفي للانطلاق (مثال: "حسّن صفحة المبيعات"، "ابدأ"). بعده **لا تتوقف** بين المراحل ولا تطلب أوامر تنفيذ جديدة.
- إن كان النطاق غامضاً: سؤال واحد بالأداة المخصصة يعرض المرشحين (الأعلى leverage أولاً موسوماً "موصى")، ثم انطلق.
- التوقف الوحيد المسموح: نهاية السطح — تقرير + اقتراح السطح التالي. لا تعديل لكود المنتج في مرحلة التدقيق أبداً.
- المحظورات الدائمة: لا commit ولا push ولا تثبيت حزم ولا فورمات ولا ميزات جديدة ولا قرارات منتج مخترعة.

## 2. المراحل الخمس

### المرحلة 1 — اختيار السطح
- سطح واحد متماسك يمثل مهمة منتج أساسية (عائلة صفحات لا الصفحة كلها إن ترابطت).
- ابدأ من المسارات والتخطيطات، وتتبع مسار العرض: مسار (Route) ← صفحة (Page) ← تخطيط (Layout) ← مكونات (Components) ← بدائيات (Primitives).
- صرّح بالاختيار ولا تخلط التطبيق كله في منتج واحد.

### المرحلة 2 — تدقيق قراءة فقط
- لا تنشئ/تعدل أي ملف منتج. مسموح القراءة والبحث فقط.
- أعد بناء النظام المحلي: التوكنات والمتغيرات والبدائيات الحاكمة لمسار العرض فقط (تتبع مثبت بالاستيراد/الخصائص/الوراثة — لا بالأسماء المتشابهة).
- افحص: النصوص الظاهرة، المحاذاة، فروع الشاشات، والمتغيرات الشقيقة لنفس المهمة — كلها **مرشحات** لا نتائج.
- سجّل كتلة `Design language` (السطح، المصادر، القرارات الموثقة، المالك/المستهلكون، الاستثناءات الصريحة).

### المرحلة 3 — بوابة الإثبات والتنقية
المرشح لا يصبح نتيجة إلا بثلاثة أدلة معاً، وإلا يُحذف:
1. **العقد (Contract)**: قرار تصميم ملزم لهذا النطاق، أو تناقض مباشر في العرض/النص داخل نفس المهمة (التكرار والأسماء وغياب الاستثناء ليست عقداً).
2. **التشغيل (Runtime)**: إثبات وصول المالك/القيمة للسطح عبر مسار العرض المتتبع (لا تقارن طبقات ملكية منفصلة).
3. **التصحيح (Correction)**: تغيير واحد تحدده الأدلة، بتوكن/متغير/نموذج موجود مسمّى بالضبط (إن تعددت الحلول أو تطلبت اختراع نية → مرفوض).
- اسقط تلقائياً: الوصولية (HTML/ARIA) إلا بطلب صريح، والسلوك وإدارة الحالة والأداء والمعمار وجودة الكود (إلا بعقد تصميمي يحكمها).
- حاول تفنيد كل مرشح بإعادة فتح مصادره؛ احذف ما يطابق التنفيذ تقريباً لا تماماً. رتّب الباقي (ثقة، أثر، انتشار، تكلفة) وقف عند **3**.

### المرحلة 4 — الخطط
- خطة لكل تغيير (لا لكل عرَض) تحت `design-plans/NN-slug.md` بترقيم متسلسل (NN = التالي بعد آخر ملف).
- كل خطة مكتملة السياق (منفذها لا يعرف المحادثة): المشكلة ← الدليل (عقد+تشغيل) ← التغيير الواحد (قبل/بعد حرفي) ← خطوات المنفذ ← التحقق ← خارج النطاق + رقم الكوميت المرجعي.
- لا توكنات مخترعة: انسخ المالك أو النموذج الحي (Exemplar) الموجود.

### المرحلة 5 — التنفيذ بالتتابع والتحقق
- فروقات صغرى فقط؛ تعديلات نفس الملف **بالتتابع** لا بالتوازي.
- توسيع شقيق مسموح فقط لإصلاح ميكانيكي بنفس السبب الجذري (نفس القاعدة حرفياً) — ويُوثّق في التقرير؛ ما عداه سطح جديد.
- بعد كل خطة: `git diff` للملفات المستهدفة + `npx tsc --noEmit` ناجح + بحث يؤكد صفر بقايا (grep للنمط القديم).
- حدّث حالة الخطة إلى `منفذة (Done)` مع ما تم فعلاً.

## 3. أوامر التحقق
- `git rev-parse HEAD` — المرجع قبل الكتابة.
- `git diff -- <ملفات>` — مراجعة الفروق المستهدفة فقط (الشجرة قد تحوي شغلاً آخر — لا تمسه).
- `npx tsc --noEmit` — بوابة النجاح لأي تغيير واجهة.
- بحث `grep` للنمط القديم بعد الإصلاح — يجب أن يبقى المستثنى بعلة فقط.

## 4. قالب الرد الإلزامي (عربي دائماً)
كل رد فيه اقتراح أو تنفيذ يجب أن يحوي:
- **التحليل**: فهم المطلوب والنطاق.
- **التصميم**: هيكلة الحل وتدفق العرض.
- **الهيكلة**: جدول `| الملف | الدور |`.
- **شرح الملفات والدوال**: الغرض + المدخلات ← المخرجات لكل ملف/دالة.
- اشرح كل مصطلح تقني بالعربي أول ورود (مثال: مسار Route، متحكم Controller، بدائية Primitive، نموذج Exemplar).
- نقاط موجزة فوق الفقرات؛ بلا حشو ولا مديح.
